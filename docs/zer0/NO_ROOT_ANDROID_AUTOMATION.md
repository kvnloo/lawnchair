# No-root Android automation: capability and integration survey

**Date:** 2026-10-18. **Target:** Galaxy S25 Ultra, Android 17 / Samsung One UI, `kvnloo/lawnchair` experimental HyprSpaces + z0live. **Status:** source/documentation audit, **not** device-validated; compatibility, background behavior and vendor features must be tested on the exact handset. This is a survey of the relevant ecosystem, not literally every Play Store automation utility.

## Privilege ladder (most reliable route first)

1. **App-owned Android APIs and explicit intents/shortcuts**: launcher actions, notifications, media controls, deep links and APIs exposed by consenting apps. No elevated privilege.
2. **User-authored trigger/condition/action tools**: Tasker, Automate, MacroDroid, Samsung Modes and Routines. Deterministic automation; each tool runs under its granted permissions.
3. **AccessibilityService, user explicitly enables**: accessible-node inspection, semantic clicks, global Back/Home, gestures and text when supported. Cannot read every surface or bypass protected/secure UIs. General-purpose autonomous AI control through AccessibilityService is prohibited by current Google Play automation policy, even if the end user consents. Never market as unrestricted.
4. **Shizuku / authorized wireless ADB shell**: package management, activities, settings, window/task inspection, shell `input` and selected privileged operations **only if allowed by that Android build**. Shell is not root or a system app. Shizuku wireless start must be reauthorized after reboot; pairing is an explicit user action.
5. **Existing Tern / Hermes / OMP Wi-Fi ADB**: working local external-control backend and fallback; may be less native, requires authorization and running service.
6. **True root / privileged OS signatures**: not available and **not** a target. Arbitrary window compositor control, secure-app data access, protected settings and freeform window privileges must not be promised.

## HyprSpaces architecture choice

- **Do not make Lawnchair depend on Tasker, MacroDroid, Shizuku, Tern or a subscription.** Keep `PhoneAction` / `PhoneActionReceipt` typed, consented, replay-resistant and provider-neutral.
- Execution backends in priority order: (1) Lawnchair owned operations/app intents/shortcuts, (2) task exported by consenting installed automation app, (3) **narrow** accessibility service after user permission and distribution-policy review, (4) approved Shizuku/ADB on opted-in advanced builds, (5) existing Tern / Hermes / OMP authorized Wi-Fi ADB. Never silently pair ADB or elevate.
- Observer: app-owned semantic state first; user-permitted accessibility nodes next; explicitly approved screenshot/remote only when necessary. Reject actions in sensitive contexts; require confirmation for messaging, purchasing, posting, data deletion, credentials and security settings.
- `VoiceSource` choices: ChatGPT app handoff; partner-approved Sign in with ChatGPT (capability gated); OpenAI API Realtime using server-minted ephemeral token; Android recognizer/on-device STT; Gemini app handoff; Tern-z0live voice; optional local models. A provider being installed does not imply an API for its microphone audio.
- Android launcher permission is **not** a compositor privilege: split screen and app bubbles can be OEM/system-locked. Request and verify outcomes, never assert actual tiling from an Intent return.
- Security: bounded allowlist, user-owned approvals, foreground-revision checks, user interrupt/cancel, signed/local actor IDs, per-action receipts and no remote arbitrary shell execution. One mic owner at a time, explicit foreground service policy, clear stop controls.
- Distribution: Google Play policy explicitly forbids general-purpose autonomous AI agents using AccessibilityService; verified disability accessibility tools have a distinct policy path. Keep experimental native computer use downstream/sideloaded until policy is reviewed; prefer deterministic rule-based, narrow automation for public distribution. [Google policy](https://support.google.com/googleplay/android-developer/answer/10964491).

## Upgrade / Sign in with ChatGPT gate

As of the current OpenAI docs, approved partners may support ChatGPT account sign-in and, **separately**, user-authorized sharing of eligible plan usage. User plan usage maps to supported Work/Codex capabilities; **Realtime Voice inclusion is not established**. The client ID is select-partner/onboarding-gated, and the developer Realtime API requires its own backend credentials and a short-lived client token. Do **not** capture browser cookies, consumer ChatGPT OAuth tokens from Hermes/OMP, or misrepresent authentication as functional. Prefer: a disabled-but-explained “Connect ChatGPT plan (partner approval needed)” capability, native OpenAI API via trusted ephemeral-key backend, and consumer ChatGPT app handoff, all independently testable.
